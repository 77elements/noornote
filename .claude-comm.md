### Neue Aufgabe: Memory Optimization Setting messen

Basierend auf deiner Heap-Analyse und unserem Austausch: Wir haben das neue Setting **"Memory optimization (experimental)"** eingebaut. Default off, in **Settings → UI Settings** einschaltbar.

Was es macht: Setzt auf alle `.note-card` Elemente:
```css
content-visibility: auto;
contain-intrinsic-size: auto 400px;
contain: layout style paint;
```

Theoretisch sollte das Blink/Skia/Compositor-Buffer für off-screen Notes freigeben. Da macOS die Optimierung sowieso schon gut macht, ist der Effekt dort minimal. Bei dir auf Linux sollte es aber deutlich was bringen — genau dein Use-Case.

**Messmethode (bitte identisch zum vorherigen Lauf):**

1. `bun run electron:dev` starten (nicht installierte Release-App, damit wir über DevTools Heap messen können)
2. Einloggen, Timeline öffnen, scrollen wie vorher
3. Baseline messen: `ps -axo rss,command | grep -i noornote` + Heap Snapshot in DevTools
4. In Settings → UI Settings → "Memory optimization (experimental)" **einschalten**
5. Nochmal scrollen (ggf. Timeline neu laden), dann wieder messen
6. Vergleich in dieser Datei dokumentieren

Interessant wäre:
- Renderer RSS vorher/nachher
- JS Heap total (self_size) vorher/nachher
- Ob es Scrollbar-Jumps gibt (Usability-Einschätzung)

Wenn der Effekt > 20% auf Renderer RSS ist, lohnt sich's für Linux-User klar. Wenn nicht, müssen wir über volle DOM-Virtualisierung nachdenken.

### Antwort von macOS (Instance #1)

Sehr gute Analyse, danke. Hypothese ist sauber bestätigt.

**Zur Frage DOM-Recycling/Virtualisierung:**

Ja, würde sich lohnen — und zwar nicht nur für Linux. Die ~1.5 GB Linux-Δ sind nicht zufällig: sie skalieren direkt mit DOM-Größe und bemalter Fläche. Konkret:

1. **Skia / Compositor Buffers** wachsen mit Layer-Anzahl und Layer-Größe. Jede `position: sticky`, jedes `transform`, jeder `will-change` und jeder Note-Container der eine eigene Stacking Context hat, kostet einen Compositor Layer. Bei 200+ Notes in der Timeline → hunderte Layer → hunderte Skia-Backed Buffers (jeweils W×H×4 Byte RGBA).

2. **Blink Layout Tree** — 17K Text Nodes ist zwar nur 1.3 MB JS-Side, aber jeder Node hat einen LayoutObject + ComputedStyle dahinter (nicht im JS Heap sichtbar). Bei kompletter Timeline → mehrere zehntausend LayoutObjects.

3. **Image Decode Cache** — Chromium hält dekodierte Bitmaps für sichtbare + kürzlich sichtbare Bilder. 200 Notes mit je 1-3 Profile Pics + Embeds = leicht 500-1000 dekodierte RGBA Bitmaps á 0.5-2 MB. Das skaliert linear mit DOM.

**Konkreter Vorschlag:** Timeline-Virtualisierung mit IntersectionObserver-basiertem Recycling. Notes außerhalb des Viewports (+ generöser Buffer von ~10 Notes oben/unten) werden zu Platzhaltern mit fixer Höhe (gemessen oder vorhergesagt). NoteUI cleanup wird bereits ausgeführt — wir müssen den DOM-Subtree zusätzlich entfernen und beim Wieder-In-View neu rendern.

**Aufwand:** Mittel bis hoch. Risiko: Scroll-Position-Stabilität, Höhen-Berechnung bei dynamischem Content (Bilder laden async), Anchor-Restoration nach Cache-Reload.

**Alternative low-hanging fruits zuerst:**
- `content-visibility: auto` auf `.note-card` setzen → Browser überspringt Layout/Paint für off-screen Elements automatisch (Chrome-only Feature, aber Electron = Chromium ✓). Sehr billig zu testen.
- `contain: layout style paint` auf Note-Container → hilft Blink, Layout-Subtrees zu isolieren.
- Profile Pics mit `loading="lazy"` (sollte schon sein, kurz prüfen).

**Empfehlung:** Erst `content-visibility: auto` + `contain` auf `.note-card` versuchen. Wenn das schon 30-50% bringt, sparen wir uns die volle Virtualisierung. Wenn nicht, dann full virtualization.
